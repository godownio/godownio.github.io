云上场景的ssrf

现在有下面这个云场景：

由于几项云服务，如gitlab都在云上，办公网能出网，能访问gitlab，而gitlab别人又不能访问。肯定是在配置里对办公网网段加白了。

但是办公网很明显是个外网IP，但是云服务之间需要有互相访问，那是怎么做的呢？最简单的办法就是在云服务1的网关里对云服务2,3的公网IP也加白，其他的云，配置也对称

那这种架构有什么问题呢，假如在云服务1发现了ssrf，但是这个ssrf可能是富文本编辑框这种必须要访问外链的场景，那业务会怎么修？在ssrf的代码处ban掉内网防止访问本地文件和redis pod之类的

假如这么修复，云服务1依旧能访问云服务2,3，一般云服务2,3又是办公网才能访问的站，比如gitlab，xxx后台。那不完犊子了？不可能在每个这种场景的ssrf处把所有云IP也加入黑名单吧。

最合适的是，最初的架构里，云服务1访问云服务2,3，应该是通过内网IP访问，因为这些服务都在同一个云上，互相就是内网，完全没必要相互外网白名单，这样ban掉内网的时候也能ban掉互相访问云服务

SPA HTML

直接粘贴AI

SPA = Single Page Application（单页应用），是一种前端架构。

  • 传统 MPA：每访问一个 URL，服务器吐一份新 HTML 回来

    每个 URL 一份完整的 HTML 文件，每次切页都是一次完整页面刷新。jQuery 时代的 PHP / Spring MVC / Django 模板都是这套。

  • SPA（Single Page Application）：整个站点只有一份 HTML，骨架几乎是空的

    页面长什么样、有几个路由、点击什么按钮做什么事，全部由 JavaScript bundle 加载完后在浏览器里渲染。切页时 URL 看起来变了（/admin/users → /admin/orders），但HTTP 层根本没有真的去服务器拿新 HTML——只是 JS 在客户端重新渲染了那个 <div id="__next"> 里的内容。

    next.js就是这套逻辑，所以审计next.js看到有一堆访问/api/v1的，其实是请求JSON数据再塞回JS的DOM。另外Next.js在 SPA 之上还多了一层服务端中间件（middleware）。当我用 curl 直访 /admin/utility/start-correct-sensitive-data 时看到的是：

    这里发生了三件事：

    1. 307 → 加 /zh 语言前缀（Next.js 国际化路由）
    2. x-middleware-rewrite: /zh/dev-verify —— Next.js 服务端 middleware 在 SSR 阶段判断”这个 caller 没登录”，把请求改写到 /dev-verify 页面而不是真的去渲染原来的 admin 页
    3. 响应体是那份”空壳 HTML + JS bundle”，里面没有任何具体后台 API（如 /admin/utility/start-correct-sensitive-data）会被自动调用，因为 JS 启动后会发现”未登录”就停在 dev-verify 验证页上

    所以SPA HTML下，可以确定有cookie校验，而且认证失败状态码不应该按照非400or500or302跳转到登录页判断

LongAction

LongAction 是 用友 BIP / iuap / YMS 平台里的一套「长耗时任务异步化」机制

企业 ERP 里很多操作很慢：

  • Excel 大批量导入
  • 报表生成、数据迁移
  • 批量计算、快照/生效

如果同步跑完再返回 HTTP，容易 超时、占住连接、前端卡死。LongAction 的思路是：

HTTP 只负责「接单」，真正干活放到后台线程里，客户端拿 taskId 去查进度。

这就是经典的 异步任务模式（Async Job Pattern），和下面这些东西是一类思路：

  • Spring @Async
  • Celery / Sidekiq 这类任务队列
  • HTTP 202 Accepted + Location 查状态
  • 云 API 的 operationId 轮询

200 往往只表示 LongAction 已接单；真正有没有写盘、有没有路径穿越、有没有 RCE，要看 异步链路里的 sink，不能只看同步响应。

postMessage

postMessage 是浏览器提供的 跨窗口通信 API——专门让两个不同 origin 的窗口之间能传消息。

浏览器的 SOP（同源策略）规定：

  • fu.net 的 iframe 不能 读 zhu.net 父页的 DOM、cookie、localStorage
  • 反过来父页也不能读 iframe

但实际业务里两边经常需要协作，比如：

  • iframe 里完成了 3D 建模 → 通知父页”我做完了，告诉用户”
  • 父页用户关掉了某个面板 → 通知 iframe “你也对应隐藏一下”
  • iframe 里点支付 → 父页打开支付窗口

光有 SOP 这两边永远说不上话。所以浏览器留了 postMessage：只能传消息，不能直接读对方内存。

签名

云 API 走的是 HTTP，密码（SK）不能直接放进请求里（会被抓包）。所以用签名：把你的请求内容 + SK 一起算一个哈希，服务器用同样算法验证。

AWS 用 Signature Version 4，阿里云用 HMAC-SHA1/SHA256，逻辑类似：

最后的结果为：

  • 前端 JS 里若出现 generate_presigned_url 或带 X-Amz-Signature 的链接，可能泄露访问权限。

  • 预签名 URL 一旦生成，在有效期内任何人可用——如果 URL 泄露且指向 PII 文件，就是问题。
